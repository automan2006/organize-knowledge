# 用户图片和助手示意图完整归档

图片是必交付内容，不能仅登记文件名、图注或“图片待上传”就结束。只要源文件和传输能力可用，就必须实际上传、插入页面并回读。全文仍可部分保存，但有任意缺图时总状态必须为“部分完成”，首段报告缺图，不称“全部完成”。

## 1. 盘点并获取源文件

分别登记 **用户上传的所有图片**（教材页、照片、截图、用户画图）和 **助手回答中展示的所有图片**（生成图片、示意图、实物配图、搜索/引用的图片、图片网格/轮播卡片、Python 绘图及图表、可视化截图、SVG/Mermaid 等图解）。只要与知识解释有关，都属于归档范围，不因其不是生成工具返回的附件而遗漏。原图、关键局部放大图和有独特信息的修改版都保留；完全重复图片可共用一个上传，仍记录对应关系。不把模板参考图混入学习配图。

每图记录：编号、来源类别、主题、来源消息定位、真实文件路径或可读取附件来源、MIME、大小、目标笔记及插入位置、上传 ID、阶段状态。仅在有真实值时记录，不能编文件路径、附件 ID 或哈希。

优先取当前会话的附件文件和生成工具返回的原文件。对实际返回的 `sandbox:` 或本地路径，通过本环境支持的文件读取方式检查；不能把它们直接当公网 URL，也不能仅因路径不是公网就跳过可读取文件。环境有文件系统时，在已知附件目录、生成输出目录中按原文件名或附件 ID 定向搜索，不扫描无关用户目录或别的聊天内容。

视图里能看见但没有可读取二进制，不代表可上传。先检查宿主支持的文件导出/附件传递能力；仍无法取得时精确报告“缺原图文件”，提示在原聊天调用本插件，或下载原图后重新作为附件提供。不能笼统归因于“Notion 不支持 GPT 图片”。

### 回答内的实物配图与图片组

参照 [回答内图片网格示意](../assets/image-grid.svg)：螺栓与螺母、螺钉、双头螺柱、垫圈这样的四格配图也必须归档。仅凭截图不能判断四张图是生成还是检索所得，按真实工具记录注明来源，不编造出处或“AI 生成”标签。

- 优先从当前对话实际可读的图像工具结果、图片卡片数据或附件找到各原图路径/原始直接 URL；若显示的是网页链接，先在有访问权限时解析实际图像来源，网页 URL 本身不能当成图片二进制上传。无来源时不得伪造文件 URL 或猜测私人链接。
- 独立原图可取得时逐张上传，将图片和对应名称、用途、与相似概念的区别放在同一小节。桌面可用两列图片卡片排版，每张图片保留独立图注；手机仍由 Notion 顺序堆叠。
- 如果原始产物是一张四格拼图，保存整张原始拼图，在其下按格子位置逐项解释；不要强行切成四张后宣称是四个原图。
- 如果当前只收到整屏手机截图，就保存这张用户截图并注明“含界面、遮挡或裁切的截图”；其中四张展示图片分别记“独立原图未取得”，不能把一张截图计作四张原图已保存。默认不重绘或替换原图；裁剪/拆图属于额外编辑，先确认用户是否要求并使用环境实际支持的图片编辑方式。
- 一张截图可以帮助复习和识别缺图，但不抵消独立原图的待补状态。有来源标记/原始链接时一并保存，不能抹掉出处。

这些布局示意只指导插件行为，不自动插入每一篇课程笔记。实际归档应保存该次聊天里的图片。

## 2. 选择可执行的上传路径

以实时 Notion schema/权限为准，以下路径依次选用：

**A. 有可读取的本地 JPEG/PNG/其他图片和 Python 执行环境**

1. 调用 `create_file_upload(filename=真实文件名)`，取得同一连接的短期上传响应。
2. 将响应放入私有临时 JSON 文件或 stdin，不放入笔记、插件源码、备份包或公开输出。
3. 运行随包的 [上传程序](../scripts/upload_notion_image.py)，它会把真实文件 bytes 以 multipart `file` 字段发送一次 POST，而非只申请上传地址。无第三方依赖，使用当前连接返回的授权，无须用户提供 Notion API key。

```text
python scripts/upload_notion_image.py --file ORIGINAL_IMAGE_PATH --prepare-json PRIVATE_TEMP_JSON --output PRIVATE_RECEIPT_JSON
```

脚本路径相对本 Skill 目录，实际使用时解析成当前安装目录，不能假设用户电脑的 D 盘路径。上限 20 MiB 是此单段流程上限，还要遵守工作区和图片显示限制。脚本仅接收当前工具返回的 HTTPS api.notion.com 地址，禁止跳转和凭据外发；将来工具改变上传域名时先核实当前工具契约再适配，不强行使用旧程序。

脚本输出的 `markdown_source` / `suggested_markdown` 是待插入附件凭据；上传成功不等于已保存在笔记。网络或上传结果不明先核实状态，不自动反复 POST。短期授权到期可重新申请一次；仍失败就记录具体阶段，保留已成功项目。清除本次程序创建的临时授权文件，仅限这些精确路径。

**B. SVG 或可读取的文本图像源**

已存在且可读取的 SVG 原文可以通过 `create_attachment(content=SVG原文, filename="图名.svg")` 直接存入 Notion，无需本地终端。检查 MIME 和实际图像引用。PNG/JPEG 二进制或其 base64 不能塞入 `content` 冒充 SVG。

Mermaid、可执行绘图代码或 HTML 图解先保留原始源；有渲染工具时从该源导出图片再走 A，同时保留源附件。只有源代码时可以保存原生图表代码块并明确“已存图源、尚未验证图片呈现”，不能计入原图已上传数。不要根据描述新画一张图冒充已丢失的原示意图。

**C. 已有直接 HTTPS 文件 URL 或同一连接已上传的文件 ID**

`create_attachment(source_url=...)` 可复制可直达且无需额外登录的原文件；`source_file_id` 只能用同一 integration 已上传完成的真实 ID。Notion 会自行获取 URL，不支持重定向、cookies 或自定义请求头。不能把 ChatGPT 会话链接、宿主附件 ID、Windows 路径、`sandbox:` 地址当成这两种来源。

**D. 手机/网页没有传输能力**

优先使用该宿主实际提供的文件与网络执行能力；脚本不能让没有 Python 或文件访问权限的环境凭空获得能力。B/C 可用时用 B/C。均不可用时必须标“待提供原图”或“当前宿主无法传输二进制”，列出具体缺图和补传方式；不要声称三端全自动已实现。保留不完整笔记及恢复位置，后续拿到附件直接补图，不要求用户重做全文。

## 3. 插入、验证与恢复

上传完成立即用返回的建议 Markdown 插入目标专题，或用真实 `file-upload://...` 图像源和完整图注构造图片块。上传尚未附着时会过期，不能只把上传 ID 留在聊天里。

原图放在对应知识点附近；复杂图独占宽行，右侧示意区可保留索引。每图附图名、知识点、读图顺序、标记/坐标/条件和复习问题。看不清不编数值；生成图有文字或尺寸错误时标明并以核实正文为准。

Fetch 回读页面，逐图核对实际 image 块、caption、已解析文件引用。缺失则做一次定点补插，保留人工正文和其他图片。仅“存在图片 Markdown”不能证明传输完成；仅文件名或文本路径不能算 image 块。若回读不完整或未知块导致无法验证，标“已写入待验证”，不计入已验证保存数。

分别报告：用户图片已验证数/发现总数、助手示意图已验证数/发现总数；另列缺原图、上传失败、已上传待插入、已写入待验证。未完整读取历史时总数只代表当前可访问内容，不能报全部聊天图片已覆盖。

后续补传请求：读取原笔记的图片清单并核对已有图像，只补缺图及必要图注，不重建同内容笔记。不要为上传发布公共图床、修改分享、索取凭据，或替换用户原图。格式转换保留原文件与来源，结果清晰可读时才作为附加版本。

Obsidian 有实际交付的原文件时用 `![[assets/文件名.ext]]` 并提供文件；否则保留图注和待手动复制提示。Notion 临时签名下载 URL 不能作为永久 Obsidian 图片路径。
